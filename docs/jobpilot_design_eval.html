产品思考：为什么做、给谁、跟谁比

先想清楚问题和定位，再写第一行代码。

问题 & 用户

痛点在「准备」，不在「投递」

主动求职的人（尤其多渠道海投的留学生、转行者），真正耗时间的是把岗位散在 Boss、小红书、各种网站上逐个看 JD、判断匹不匹配、再逐份改简历——重复、累、还容易漏。但全自动投递又不可信、有风险：投错不可逆，用的还是你真实账号。

所以我的判断：把「找 + 判断 + 改」自动化，把「投不投」留给人。价值在准备，风险点留人工。
同类做法代表他们怎么做JobPilot 的不同
平台自带 AIBoss / 猎聘「AI 找工作」绑单一平台，黑箱推荐，看不到为什么推这个多渠道聚合，打分给可解释理由，不绑平台
AI 简历工具各类简历优化器只改简历，容易加上你没有的技能（注水）patch 不重写 + 技能白名单，不造假、不动格式
通用 agent 框架搭的LangChain / AutoGPT 式全自主、让模型自己决定下一步，易跑偏、不可控半自主，控制流写死，不自动投递
AI 招聘方OpenJobs / Mira 这类招聘方视角，帮 HR 找候选人同一领域的求职方镜像，帮候选人，逻辑同构
一句话定位：市面上要么绑平台、要么全自动黑箱、要么只改简历。JobPilot = 多渠道聚合 + 可解释打分 + 人做最后决定 + 不造假不爬虫（合规）。差异不在「更智能」，在高风险场景里更可控、更可信。

关于市场，我会诚实说

我没有精确的市场份额数据，上面是定性的定位对比，不是市场规模测算。求职工具是个拥挤赛道，我做的不是「再造一个更大的」，而是验证一个具体判断：多渠道 + 人在最后一环这种形态，对真实求职者是不是更靠谱。

一条主数据流，串起整个链路

没有一上来堆功能；先定主数据流，再让每一步失败彼此隔离——一个死掉的渠道不会拖垮全程。

五个关键设计判断

每一条都能扛住「你凭什么这么做」的追问。

Agent 架构

半自主，不是全自主

全自主 agent 把控制流交给模型自己决定下一步、何时停（ReAct 那类）。强，但会跑偏、不可控、不可解释。我把控制流用代码写死，LLM 只在打分/写话术这种点被调用。

能用代码写死的控制流，就别交给模型。不确定性只留给真正需要判断力的点。
可靠性

AI 可选降级

没有 API key 也能跑：打分降级到启发式加权规则，搜岗、追踪、漏斗这些核心功能照常用。LLM 是增强项，不是地基。

做这个降级最大的收获不是容错，是逼我想清楚——哪些功能离了 LLM 根本不成立。
LLM 可控性

简历定制：patch 不重写

AI 直接生成整份简历会改乱格式、还会加我没有的技能。所以我让它只产出改好的文字，再用文本对齐（difflib）patch 回原 .docx，字体排版分毫不动；技能走人工白名单。

默认 AI 输出不可信，在「它会乱来」的前提下设计系统。
可信建议

军师：算账与说话分离

diagnose() 纯代码算诊断——漏斗、高分岗缺口、停滞数，每个数字都追溯回一条数据库查询、可测试、不调 LLM。generate_advice() 才把这些数字喂给 Claude 翻成人话。

算账归代码、说话归模型，LLM 碰不到事实只碰措辞。建议才扛得住「你凭什么这么说」。
工程基础

选型匹配规模，不是越重越好

adapter 模式隔离平台差异——每个渠道返回格式都不同，上层只认统一接口，加渠道就是新写一个 adapter。SQLite（WAL + connection-per-call）：单用户本地工具，没有并发写、不需要网络访问，一个文件零运维——多用户在线了才该换 Postgres。frozen dataclass：数据建好就不可改，要改生成新副本，确定没有函数在暗处偷偷改了岗位数据。

先写测试再实现——现在 495 个测试全过。单元测试 mock 掉 AI 只验我的逻辑；模型质量另走 eval（见下）。

两段式打分：用便宜方式跑大多数岗位，只在关键点花钱

这是 JobPilot 一个我反复思考过的设计决策——本质上是用最简单的方式做模型路由。

问题：用 LLM 给所有岗位精细打分要花多少钱？

用 Claude 给一批岗位（约 350 个）按 5 维度精细打分，单次成本约 7 美金。每周跑 3-5 次完整 pipeline，一周就要 100 美金，两个月烧光预算——产品根本跑不到验证想法那天。

解法

把"打分"这件事拆成两段

第一段（规则筛）：所有岗位过一遍——关键词匹配、薪资硬过滤、学历过滤、地点过滤。免费、毫秒级、覆盖全部。出来一个粗排序，把明显不匹配的剔除。

第二段（LLM 精评）：只对 Top 20 调 Claude API 做 5 维度精细打分（技能、经验、学历、岗位相关度、偏好）。这是真正花钱的部分，但只在最有可能投的少数岗位上花。

简单任务用便宜方式，复杂任务用贵方式——这是路由的本质。我没用 ML 模型做选择，规则启发式已经够用。

「AI 可选降级」到底降的是什么？

把功能按对 LLM 的依赖分三桶，比笼统说「能降级」更扛追问。

纯代码 不碰 LLM

无 API key 照常跑
  • 投递追踪 / 漏斗 / 日报
  • 军师 diagnose() 诊断
  • 跟进提醒 · 状态机
  • difflib patch + 白名单机制

能降级 enhanced

退到确定性版本，核心还在
  • AI 打分 → 启发式加权
  • 军师建议措辞 → 退回数字诊断

替代品本身诚实有用（规则排序真能排序）。

不该降级 essential

价值就在语义理解
  • 简历语义重组
  • 多轮对话军师 / 面经识别
  • 简历结构化解析

没 key 时诚实退回（导出 prompt），不用模板假装。

降级的底线：绝不用低质量替代品冒充高质量功能。能降级的（打分）替代品本身有用；不能降级的，我退回到确定性事实，宁可少给，不给假的——这跟军师「数据不足拒绝硬编」是同一个判断。

Eval 思路：怎么知道 AI 打分不是瞎打？

先度量，再调权重——你没法在没测之前就去调权重对不对。

问题：AI 给岗位打的 1–10 分，到底跟「我真正想投哪个」吻合多少？

把它当成一个二分类问题：预测 = 「AI 分 ≥ 阈值」，真值 = 「我会不会投这个岗」。两边一比，就能算出一致性，而不是靠感觉说「AI 挺准的」。

方法：四步

1
定义真值（ground truth）——我真实的投/不投决定，从两个来源合并（见下表）。
2
定义预测——AI 给该岗的 overall_score ≥ threshold 即「预测会投」。这一版 threshold = 7.0。
3
只统计「既有标签、又有 AI 分」的岗，逐个落进混淆矩阵 TP/FP/FN/TN。
4
算 precision / recall / F1 / accuracy，再据此决定要不要调打分权重。

真值从哪来

= 1投了 / 有回复 / 进面试 / 拿 offer → 我想要这个岗
= 0被拒（我投了但没成）→ 计为负例
覆盖手动标注文件 eval_labels.json 优先级最高，覆盖上面两条

这一轮主要靠 手动标注——因为我真实投递发生在 JobPilot 之外（Boss / 邮箱直投），applied 字段在 DB 里基本空着。所以我从 372 个有 AI 分的岗位里随机抽 80 个，自己一个一个标「想投 / 不想投」。

对求职这件事，FN（把我想投的岗打了低分）比 FP 更危险——漏掉机会的代价更高。所以我会更看 recall，而不是只看 accuracy。

解读：AI 打高分的岗里 78% 是我真想投的（Precision 还行）。但**我想投的岗里，AI 只抓到了 54%——46% 被漏掉了**（Recall 明显偏低）。这是 eval 跑出来才能看到的真相，光看 AI 输出的高分列表不会发现。

关键发现：18 个 FN（AI 漏抓的好岗）有共同模式

我去逐个看 FN——AI 打了 5–6 分但我标了「想投」的岗位——发现一个清晰的 pattern：这些岗几乎全是大厂或一线 AI 创业团队的相关岗，但 AI 给它们打了低分。

典型 FN 案例：
· 字节跳动 AI 产品经理实习生 · AI 分 6.19 · 我想投
· 阿里云千问 APP 主 Chat 组 · 5.89 · Kimi 同类对口
· MiniMax AI Agent 产品岗 · 5.50 · 标题明显对口
· 上海人工智能实验室 AI 产品经理 · 6.94 · 研究院背景
· 智谱华章 产品经理（北京）· 6.16 · 大模型独角兽
· 自然选择 大模型应用产品 · 5.64 · 创业明星

根因诊断：AI 当前打分权重过度依赖标题精准度（「AI 产品经理实习生」这种关键词）——忽略了公司质量信号。大厂的相关岗即使标题模糊也应该被推荐，但当前模型给不了高分。

下一步：加 company_tier 权重，重测对比

改动
在打分 prompt 里加 company_tier 一档：独角兽/大厂/知名 AI 创业团队 → +1 分；信息不全/不知名小公司 → −0.5 分。
成本
~1 小时 prompt 改 + 重跑 eval。这是低成本高回报实验。
目标
Recall 从 0.538 提到 ≥ 0.75，同时 Precision 不能掉到 0.65 以下（避免过度推大厂）。
退出条件
如果 Recall 上去但 Precision 崩了（FP 大量增加），说明 company_tier 权重太大，需要回退或细分。

Measure → Diagnose → Change → Re-measure。这是 PM 的标准动作——不是「感觉这个权重该调」，是「数字告诉我哪个权重该调」。

业务取舍：为什么我盯 Recall，不盯 Precision

求职是个代价不对称的场景——两种错误的代价完全不一样：

FP · 推错
AI 推一个我其实不想投的岗 → 我看一眼标题就划走，成本 30 秒。
FN · 漏掉
AI 漏掉一个我应该投的好岗 → 我可能错过一份心仪 offer。

结论：求职 ToC 工具应该 Recall 优先。如果场景换成企业风控 / 合规审计，FP（误推一个违规）代价比 FN 大，那就反过来 Precision 优先。指标重点取决于业务，不是默认看 F1。

形态选择：为什么这套 eval 是单函数，不是 harness

我另一个项目（MusiClaw）的 eval 是完整 harness 结构——cases/ + judges/ + runner.py + results/，因为它评的是 agent 跑工作流的行为，每个 case 是一个独立任务，需要注入 fixture、跑 agent、看 trace 对不对，还要 pass@k 多次重跑。

JobPilot 这套 eval 形态完全不同——评的是 AI 打的分跟我的判断一不一致（scoring agreement）。所有岗位是同一类对象，AI 分已经存在 DB 里、不会变，不需要 fixture、不需要重跑、不需要 pass@k。一个 evaluate(db, labels, threshold) 函数 + 一个混淆矩阵就够了。

Tools should match the shape of the problem. 把 harness 当万能模板套到不需要的场景，是 over-engineering——也是很多 PM 容易犯的错。

这套 eval 的边界（我会主动讲）

这是一次 first-pass calibration——80 个样本是我对 80 个真实岗位的真实判断（我会不会投），跑出来的 0.636 F1 / 0.538 Recall 也是真实数字。但样本量还不算大，单一标注者也意味着可能有标注偏差。所以现在准确的说法是：我已经有一套能跑出数字的 eval，并且清楚它的局限，不是「我已经验证 AI 打分很准」。

能区分「eval framework 完成」和「eval 已被充分校准」这两件事，本身就是 PM 该有的诚实——比假装数字都准强。

为什么这套设计值得讲：很多人做 AI 产品停在「感觉还行就上线」。我把「AI 准不准」变成一个可证伪、能算数的问题——用我自己的真实决定当标尺。这是经济/统计训练给我的本能：先想怎么度量，再谈优化。能跑出 Recall 0.54 而不是 F1 0.95，反而让我相信这个 eval 真的在帮我看清模型——0.95 的数字往往意味着测试集有问题。
